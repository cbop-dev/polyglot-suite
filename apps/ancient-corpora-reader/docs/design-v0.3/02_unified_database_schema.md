## 1. Objective & Scope

Historically, each corpus database in ACR was compiled using disparate legacy schemas from independent prototypes:
* **Josephus** used an `attested_forms` relational table and book-only coordinates.
* **Philo** stored inflected forms in a JSON table `lemma_forms` and used chapter coordinates.
* **Apostolic Fathers** lacked any precomputed inflection table, requiring expensive runtime joins on `concordance_refs` and scans of `text_unit_tokens`.
* Client code in `dbClient.ts` was forced to branch with `if (corpusId === 'josephus') ... else if (corpusId === 'philo') ... else ...`.

This specification establishes **one canonical relational schema contract** that every SQLite database compiled for ACR must implement. When all databases conform to this contract, `dbClient.ts` executes identical SQL queries regardless of the corpus.

## 2. Canonical DDL Specification

Every compiled SQLite database (`af.sqlite3`, `philo.sqlite3`, `josephus.sqlite3`, and future corpora) shall contain the following standard tables:

### 2.1 `corpus_versions` (Text Versions & Witnesses)
Identifies the specific text versions present in this corpus database:
```sql
CREATE TABLE corpus_versions (
    id TEXT PRIMARY KEY,             -- e.g. 'lake_grc', 'yonge_eng', 'af_lat'
    language TEXT NOT NULL,          -- ISO 639-3 or BCP 47 (e.g. 'grc', 'eng', 'lat', 'hbo')
    title TEXT NOT NULL,             -- Human-readable title of this specific edition
    version_label TEXT,              -- e.g. '1912', '1856', 'Critical Edition'
    direction TEXT DEFAULT 'ltr',    -- 'ltr' or 'rtl'
    order_index INTEGER DEFAULT 0    -- Display precedence in column views
);
```

### 2.2 `corpus_works` (Works Catalog)
Provides uniform work metadata across all works in the corpus:
```sql
CREATE TABLE corpus_works (
    code TEXT PRIMARY KEY,           -- Uppercase work code (e.g. '1CLE', 'OPIF', 'WAR')
    slug TEXT NOT NULL,              -- URL-friendly slug (e.g. '1-clement', 'opif', 'war')
    order_index INTEGER NOT NULL,    -- Display sequence in pickers
    category TEXT NOT NULL,          -- e.g. 'epistle', 'treatise', 'history'
    abbrev TEXT NOT NULL,            -- Standard academic abbreviation (e.g. '1 Clem.', 'Opif.', 'BJ')
    tlg_id TEXT,                     -- TLG author/work canon ID if applicable
    title_english TEXT NOT NULL,
    title_primary TEXT,              -- Original language title (Greek, Hebrew, etc.)
    title_secondary TEXT,            -- Latin or alternative title
    total_divisions INTEGER NOT NULL, -- Total primary divisions (books or chapters)
    min_division INTEGER DEFAULT 1,  -- Usually 1 (0 for 1 Clement preface)
    division_label TEXT NOT NULL     -- 'Book' or 'Chapter'
);
CREATE INDEX idx_corpus_works_order ON corpus_works(order_index ASC);
```

### 2.3 `text_units` (Aligned Text Rows)
Standardizes primary navigation coordinates (`book`, `chapter`, `section`) and extracts edition-specific milestone markers into structured metadata:
```sql
CREATE TABLE text_units (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    version_id TEXT NOT NULL REFERENCES corpus_versions(id),
    work_code TEXT NOT NULL REFERENCES corpus_works(code),
    book INTEGER NOT NULL DEFAULT 0,
    chapter INTEGER NOT NULL DEFAULT 0,
    section INTEGER NOT NULL,        -- Primary section / verse integer
    section_label TEXT,              -- Optional alphanumeric section label (e.g. '1a', 'proem')
    display_citation TEXT NOT NULL,  -- e.g. '1 Clem. 1:1', 'Opif. 15', 'War 1.25'
    milestone_ref TEXT,              -- Secondary milestone (e.g. Niese § or Mangey milestone)
    text_content TEXT NOT NULL
);
CREATE INDEX idx_text_units_seek ON text_units(work_code, book, chapter, section, version_id);
```

### 2.4 `text_unit_tokens` (Lean Token Storage)
Decouples token payload from main text seeking:
```sql
CREATE TABLE text_unit_tokens (
    work_unit_id INTEGER PRIMARY KEY REFERENCES text_units(id),
    tokens_json TEXT NOT NULL        -- Compact JSON: [{"w":"λόγος","l":"λόγος","m":"N-NSM","p":"N"},...]
);
```

### 2.5 `concordance_refs` (Zero-Join Covering Index with KWIC)
Self-contained covering table enabling instant concordance pagination without runtime table joins:
```sql
CREATE TABLE concordance_refs (
    corpus_id TEXT NOT NULL,         -- Matches text_units.version_id
    lemma TEXT NOT NULL,             -- Normalized dictionary lemma
    work_unit_id INTEGER NOT NULL,
    display_citation TEXT NOT NULL,
    work_code TEXT NOT NULL,
    book INTEGER DEFAULT 0,
    chapter INTEGER DEFAULT 0,
    section INTEGER NOT NULL,
    milestone_ref TEXT DEFAULT '',
    matched_form TEXT NOT NULL,      -- Exact inflected surface form
    kwic_snippet TEXT NOT NULL,      -- Precomputed KWIC HTML/text snippet
    PRIMARY KEY (corpus_id, lemma, work_unit_id, matched_form)
) WITHOUT ROWID;

CREATE INDEX idx_concordance_paged ON concordance_refs(
    corpus_id, lemma, work_code, book, chapter, section
);
```

### 2.6 `lexicon_entries` & Shared Lexicons Architecture
Currently, each corpus database includes a `lexicon_entries` table:
```sql
CREATE TABLE lexicon_entries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    dictionary TEXT NOT NULL,        -- e.g. 'lsj', 'bdb', 'lewis-short'
    strongs_id TEXT,
    lemma TEXT NOT NULL,
    normalized_lemma TEXT NOT NULL,
    pos TEXT,                        -- Part of speech
    transliteration TEXT,            -- Latinized phonetics
    gloss TEXT NOT NULL,             -- Short translation/gloss
    definition TEXT NOT NULL         -- Full definition HTML/markdown
);
CREATE INDEX idx_lexicon_lookup ON lexicon_entries(normalized_lemma, dictionary);
CREATE INDEX idx_lexicon_lemma ON lexicon_entries(lemma, dictionary);
```

> [!TIP]
> **Architectural Enhancement: Standalone Shared Lexicons Database (`lexicons.sqlite3`)**  
> Currently, the massive Liddell-Scott-Jones (LSJ) Greek lexicon is duplicated across `af.sqlite3`, `philo.sqlite3`, and `josephus.sqlite3` (as well as `polyglot.sqlite3` in the Bible Reader).  
> **Recommended Target Architecture**: Decouple lexicons into a separate, dedicated `lexicons.sqlite3` database with its own GitHub Release (e.g. `lexicon-v1.0.0`).
> * **Browser Caching**: A user visiting any reader in the Polyglot Suite downloads and caches the lexicon chunks once. Subsequent lookups in Philo, Josephus, AF, or the Septuagint hit the local browser cache.
> * **Database Shrinkage**: Eliminates tens of megabytes of duplicated text and index pages from every literary corpus database.
> * **Independent Versioning**: Lexicon errata, formatting fixes, or markdown additions update independently of text revisions.

### 2.7 `lemma_forms` (Precomputed Inflections & Attested Forms)
**Resolves the Tier 2.6 omission.** All corpora pipeline builders must precompute attested inflection forms during compilation:
```sql
CREATE TABLE lemma_forms (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    corpus_id TEXT NOT NULL,         -- Primary text version ID (e.g. 'lake_grc', 'grc', 'josephus_grc')
    lemma_key TEXT NOT NULL,         -- Exact dictionary lemma
    normalized_lemma TEXT NOT NULL,  -- Accent-stripped lemma
    forms_json TEXT NOT NULL         -- JSON array: [{"word":"λόγου","pos":"N","parse":"G-GSM","count":14},...]
);
CREATE INDEX idx_lemma_forms_lookup ON lemma_forms(lemma_key, corpus_id);
CREATE INDEX idx_lemma_forms_norm ON lemma_forms(normalized_lemma, corpus_id);
```

## 3. Client Queries & VFS Performance Analysis

### 3.1 Fetching Division Text Sections: VFS Performance Evaluation

In `sql.js-httpvfs`, every database query executes against virtual chunks over HTTP range requests. Let us evaluate the performance of fetching division text units and tokens:

#### The Query:
```sql
SELECT u.id, u.version_id, u.work_code, u.book, u.chapter, u.section,
       u.section_label, u.display_citation, u.milestone_ref, u.text_content,
       tok.tokens_json
FROM text_units u
LEFT JOIN text_unit_tokens tok ON tok.work_unit_id = u.id
WHERE u.work_code = ? AND u.book = ? AND u.chapter = ?
ORDER BY u.section ASC, u.id ASC;
```

#### Performance Mechanics in `sql.js-httpvfs`:
1. **Primary Index Range Seek**:
   - The query filters on `(work_code, book, chapter)` using `idx_text_units_seek`.
   - *Crucial optimization*: Notice we avoid `(u.book = ? OR u.chapter = ?)`. In SQLite, `OR` across columns prevents a continuous B-tree range seek and triggers an OR-by-union or temporary table scan. By resolving coordinates in advance (e.g. `{book: 1, chapter: 0}` or `{book: 1, chapter: 1}`), SQLite performs a **single direct B-tree range seek**.
2. **The `LEFT JOIN` on Primary Key**:
   - `tok.work_unit_id` is the clustered primary key of `text_unit_tokens`.
   - For a typical division containing 20–80 sections, SQLite executes 20–80 integer primary key lookups ($O(1)$ each).
   - Because `text_unit_tokens` rows are inserted in sequential `work_unit_id` order during compilation, all 20–80 token blobs reside on **2 to 3 contiguous 4KB database pages**.
   - Under `sql.js-httpvfs` (with 64KB block requests or 5MB chunks), these contiguous pages are fetched in **one single HTTP range request** and cached in memory.
   - Live benchmarks from Tier 2 demonstrate division queries resolving in **under 8 milliseconds**.

#### High-Performance Alternative: Inlining `tokens_json` into `text_units`
In the initial architecture, `tokens_json` was separated from `text_units` because concordance searches joining `text_units` were pulling bloated pages.  
**However**, in Tier 2 we built `concordance_refs` as a **zero-join covering index** containing its own precomputed KWIC snippets. Concordance queries **never touch `text_units` anymore**!

Therefore, during this refactoring we have the option to:
* **Option A (Zero-Join Schema)**: Merge `tokens_json` directly into `text_units`. This eliminates the `text_unit_tokens` table entirely, reduces the query to a single-table seek without any `LEFT JOIN`, and simplifies compilation.
* **Option B (Normalized Split)**: Retain `text_unit_tokens` with the primary key `LEFT JOIN`, keeping `text_units` lean for rare metadata-only operations.

*Recommendation*: Option A (inline `tokens_json`) is faster and cleaner now that `concordance_refs` is fully covering.

### 3.2 Fetching Attested Forms
```sql
SELECT forms_json
FROM lemma_forms
WHERE (lemma_key = ? OR normalized_lemma = ?) AND corpus_id = ?
LIMIT 1;
```
*No more `if (corpus === 'josephus')` vs `else if (corpus === 'philo')` vs `else` in JavaScript.*

### 3.3 Concordance Page Fetch
```sql
SELECT work_unit_id, display_citation, work_code, book, chapter, section,
       milestone_ref, matched_form, kwic_snippet
FROM concordance_refs
WHERE lemma = ? AND corpus_id = ?
ORDER BY work_code ASC, book ASC, chapter ASC, section ASC
LIMIT ? OFFSET ?;
```
